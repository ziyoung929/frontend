# 겹 — 여섯 명의 한 시간 (반응형 웹 · 시안 A/B)

> 6명의 동료가 다음 주까지 1시간 회의를 잡는 경험. VOC 기반 문제 정의 → 가설 → UX/UI → 인터랙티브 프로토타입까지의 전 과정을 담은 케이스 스터디 + 반응형 웹 애플리케이션.

**실행** (빌드·의존성 없음, 단일 HTML):
- **시안 A · 모아서 푸는 겹** — `index.html`: 3단계 응답 수집 → 근거 있는 추천 → 확정
- **시안 B · 묻지 않는 겹** — `b.html`: 입력 0회. 캘린더 + 행동 패턴 추론으로 바로 제안 → 거부권 1비트 → 마감 시 자동 확정
풀 페이지 웹 앱으로 동작합니다 — 상단 고정 바의 "데모 바로가기"로 각 화면에 바로 진입할 수 있고, 앱 아래에 설계 노트(케이스 스터디)가 이어집니다.

## 1. 어떤 문제를 발견했나요? 왜 문제라고 생각했나요?

표면의 문제는 "다 같이 되는 시간이 없다"입니다. 그런데 6명 팀 시나리오 기반의 가상 리서치(사내 설문 n=42 + 메신저 로그 분석을 가정, 수치는 과제용 구성)를 파고들면 다른 그림이 나옵니다.

- 회의 1건 확정까지 메시지 **23회**, 평균 **2.3일**
- 확정 후 **재조율 발생률 38%**, 재조율 원인 1위는 "겹치는 시간이 없어서"가 아니라 **"응답에 담지 못한 사정"(54%)**
- **71%**가 "피하고 싶은 시간을 '가능'으로 응답한 적 있다" — "점심 직후는 피하고 싶지만 '안 된다'고 적기엔 눈치 보여서"

사람들은 시간을 찾긴 찾습니다. 문제는 확정한 뒤에 터집니다. 가능/불가 두 칸짜리 응답 포맷이 선호를 지우고(정보 손실), 필수/선택 구분이 없어 선택 참석자 한 명이 전체를 막고, 근거 없는 자동 추천은 신뢰받지 못해 결국 수동 검증됩니다. 그래서 근본 문제를 이렇게 재정의했습니다 — **"일정 조율의 실패는 탐색의 실패가 아니라, 수집 단계의 정보 손실이다."**

## 2. 그 문제를 어떻게 해결했나요?

화면마다 검증 가능한 가설을 하나씩 담았습니다.

| 가설 | 화면 | 지표 |
|---|---|---|
| **H1** '피하고 싶음'을 정식 응답 값으로 만들면 거짓 '가능'이 줄어 재조율률이 내려간다 | 참석자 응답 (3모드 칠하기) | 재조율률, '피하고 싶음' 사용률 |
| **H2** 캘린더 일정을 미리 채워 '확인과 보정'만 하게 하면 응답 완료율·속도가 오른다 | 응답 화면 프리필 배너, 응답 현황의 연동/직접 구분 | 24h 내 응답률, 응답 소요시간 |
| **H3** "누가 왜 어려운지"가 보이는 추천은 블랙박스 자동 확정보다 확정을 빠르게 하고 번복을 줄인다 | 추천 카드의 이유 문장 + 바텀시트 상세 | 요청→확정 시간, 확정 번복률 |
| **H4** 필수/선택 구분은 '가능한 시간 없음' 데드락을 줄인다 | 참석자 선택 스텝의 세그먼트 컨트롤 | 후보 0건 발생률 |

플로우: 주최자가 회의 만들기(무엇을/누구와/언제까지, 3단계 스텝 인디케이터) → 캘린더 연동자는 자동, 미연동자는 직접 응답 → 결과 대시보드(참석자 사이드 패널 + 이유가 달린 추천 3개 + 주간 히트맵) → 상세 패널(PC 우측 슬라이드 오버 / 모바일 바텀시트)에서 6명 각각의 사정 확인 → 확정(피하고 싶던 시간의 동료에게 양해, 불참자에게 노트 공유 자동 안내).

## 3. 왜 이 방식으로 설계했나요?

- **계산은 도구가, 판단은 사람이.** 조합 계산은 도구의 일이지만 "준호가 피하고 싶어해도 이번엔 어쩔 수 없다"는 판단은 팀 맥락을 아는 사람의 몫입니다. 그래서 정답 하나 대신 지형(히트맵)과 근거(상세)를 보여주고 추천은 출발점으로만 제공합니다. 각 가설을 독립된 화면 단위로 설계해, 지표가 가설을 기각하면 그 화면만 되돌릴 수 있게 했습니다.
- **선호는 절대 시간을 막지 않습니다.** 선호가 불가처럼 작동하면 사람들은 학습을 통해 선호를 다시 숨기게 되고, H1이 무너집니다. 색 농도와 순위에만 반영합니다.
- **입력은 '보정'만.** 조율 도구는 응답률이 생명입니다. 바쁜 일정은 캘린더가 알고 있으니, 참석자는 도구가 모르는 것(선호)만 얹습니다.
- **규칙은 화면이 대신 지킵니다.** 업무시간·점심 정책은 옵션이 아니라 후보에서 제외하고 미리 고지, 필수 불가 시간은 빗금과 "수민님이 안 되는 시간" 문장으로, 모바일의 밀도 제약은 칸의 의미를 '30분'에서 '그 시각에 시작하는 1시간 회의'로 재정의해 풀었습니다.

## UI 노트

토스의 디자인 언어 — 하나의 화면 하나의 질문, 큰 타이틀, 바텀시트/슬라이드 패널, 단정한 그레이 스케일, `word-break: keep-all` — 를 참고해 웹 환경에 맞게 재구성했고, 색·타이포·라운드 토큰은 자체 정의했습니다.

- 의존성 없는 단일 HTML (vanilla JS + CSS custom properties)
- 라이트/다크 테마 (`prefers-color-scheme` + `data-theme` 오버라이드), `prefers-reduced-motion` 존중
- 키보드 접근(모든 칸이 button, Esc로 시트 닫기), 스크린리더용 aria-label(시간대마다 "누가 왜" 설명 포함)
- 점수 모델: 필수 불가 = 차단, 필수 '피하고 싶음' −22, 선택 불가 −15, 선택 '피하고 싶음' −7 / 추천은 요일 다양성 페널티를 둔 그리디 선택

## 시안 B — "각자 안 되는 시간을 입력하지 않고는 못 푸나?"

시안 A는 정직하게 보면 6명 모두에게 숙제를 내는 설계입니다. 시안 B(`b.html`)는 질문을 뒤집습니다 — 필요한 정보를 분해하면 ① 확실한 불가(캘린더에 이미 있음) ② 모호한 사정(본인도 미리 형식화하기 어려움) ③ 선호(물으면 눈치가 섞임)인데, **①은 이미 있고 ③은 행동에서 추론되고 ②는 걸리는 순간에만 존재**합니다. 그러니 미리 물을 이유가 없습니다.

- **구조**: 수집→계산→선택이 아니라 **제안→거부권→자동 확정**. 참석자가 받는 건 [어려워요] 버튼 하나, 침묵은 동의(마감 고지), 거부가 오면 2순위로 즉시 재제안하고 그 신호를 학습
- **추론의 투명성**: "준호님은 13시 회의를 피하는 편(최근 8주 4건 중 3건 거절 · 신뢰도 높음)"처럼 근거·신뢰도를 전부 공개 — 블랙박스가 아니라 반박 가능한 주장으로
- **가설**: B-H1 확정 시간이 응답자 속도가 아닌 마감 시각에 종속(2.3일→수 시간) · B-H2 참석자당 액션 0~1회로 조율 회피 소멸 · B-H3 거부 1비트 축적으로 재제안 횟수 감소
- **리스크 방어**: 추론은 순위에만 영향(시간을 막지 않음), 재제안 3회 후 시안 A로 폴백, 추론 내역은 본인이 보고 끌 수 있음
- **결론**: A vs B가 아니라 **기본은 B, 중요한 조율만 A** — 두 시안은 대립이 아니라 계층
