‘피하고 싶어요’를 말할 수 있게 하면,
회의는 한 번에 잡힌다

회의가 다시 잡히는 진짜 이유는 시간이 없어서가 아니라, 눈치 때문에 ‘가능’이라고 답한 시간에 잡혀서예요 — 그래서 38%가 확정 후에 다시 잡아요. 시안 A는 응답 선택지에 ‘피하고 싶어요’를 추가하는 것으로 이 문제를 풀어요. 이 답은 시간을 막지 않고 추천 순서만 내리기 때문에, 말해도 손해가 없고 → 그래서 솔직해져요. 아래에서 직접 눌러보세요.

설계 노트
00 · 한눈 요약

무엇으로, 무엇을, 어떻게 해결하나

이 문제를이 장치로이렇게 풀어요확인할 숫자
피하고 싶은 시간을 ‘가능’으로 답함(71%) → 확정 후 다시 잡음(38%) ‘피하고 싶어요’ 응답 이 답은 시간을 막지 않고 순위만 내림 → 말해도 손해가 없어서 솔직해짐 재조율률 38%↓
안 와도 되는 1명의 일정이 전체를 막음 → “되는 시간이 없어요” 필수/선택 구분 필수의 ‘안 돼요’만 시간을 차단, 선택은 순위에만 반영 후보 0건 발생률↓
추천을 못 믿어서 결국 손으로 재확인(확정까지 2.3일) 이유가 달린 추천 “꼭 올 4명 가능 · 준호님은 피하고 싶은 시간” — 근거가 보이면 검증이 필요 없음 요청→확정 시간↓
6명이 시간표를 채워줄 때까지 기다림 캘린더 미리 채움 입력이 ‘작성’에서 ‘확인’으로 줄어듦 24시간 내 응답률↑
01 · 문제 정의

“빈 시간을 못 찾는 것”은 표면이었다

처음 들리는 문제는 단순해요 — “다 같이 되는 시간이 없어요.” 그런데 6명 팀 시나리오로 인터뷰와 로그를 들여다보면 다른 그림이 나와요. 사람들은 시간을 찾긴 찾아요. 문제는 확정한 뒤에 터져요.

“단톡방에 ‘다들 언제 돼요?’ 올리면 하루가 그냥 가요. 답이 반만 모여서 결국 제가 표를 만들어 돌려요.”

회의를 자주 주최하는 PM

“점심 먹고 바로는 정말 피하고 싶은데, ‘안 된다’고 적기엔 눈치 보여서 그냥 ‘가능’으로 눌러요. 그리고 당일에 힘들어하죠.”

백엔드 엔지니어

“저는 참고만 하면 되는 회의인데, 제 외근 일정 때문에 전체가 일주일 밀리는 게 미안해요.”

주 2회 외근하는 데이터 분석가
23회
회의 1건 확정까지 오간 메신저 메시지
2.3일
요청부터 확정까지 걸린 평균 시간
38%
확정 후 재조율이 발생한 비율
71%
“피하고 싶은 시간을 ‘가능’으로 응답한 적 있다”

* 과제 시나리오를 위한 가상 리서치 설정입니다(사내 설문 n=42 + 메신저 로그 분석을 가정). 수치는 “무엇을 측정해야 문제를 증명할 수 있는가”를 보여주기 위해 구성했어요.

재조율의 1위 원인은 “겹치는 시간이 없어서”가 아니라 “응답에 담지 못한 사정”(54%)이었어요. 가능/불가 두 칸짜리 응답 포맷이 선호를 지우고, 지워진 선호는 확정 후에 비용으로 돌아와요. 그래서 근본 문제를 이렇게 다시 정의했어요 — “회의가 안 잡히는 건 시간이 없어서가 아니라, 묻는 방식이 사람들의 사정을 지우기 때문이다.”
02 · 가설

화면마다 가설이 하나씩 있다

문제 정의에서 가설 4개를 세우고, 각 가설을 검증할 화면과 지표를 먼저 정한 뒤 UI를 그렸어요.

H1 · 응답 포맷

‘피하고 싶어요’라고 답할 수 있게 하면, 마지못해 누른 ‘가능’(71%)이 줄어 다시 잡는 일(38%)도 줄어들 것이다.

화면 → 참석자 응답지표 → 재조율률 · ‘피하고 싶음’ 사용률
H2 · 입력 비용

캘린더 일정을 미리 채워두고 ‘맞는지 보고 고치기만’ 하게 하면 더 많은 사람이, 더 빨리 답할 것이다.

화면 → 응답 화면 · 현황지표 → 24시간 내 응답률 · 응답 소요시간
H3 · 판단 근거

“누가 왜 어려운지”가 보이면 더 빨리, 더 마음 편히 확정할 것이다. 이유가 보여야 결정을 믿을 수 있으니까.

화면 → 추천 결과 · 상세 패널지표 → 요청→확정 시간 · 확정 번복률
H4 · 참석 가중치

필수와 선택을 나누면, 안 와도 되는 한 사람 때문에 ‘되는 시간이 없어요’가 되는 일이 줄어들 것이다.

화면 → 참석자 선택 · 결과 사이드 패널지표 → 후보 0건 발생률
03 · 설계 원칙

계산은 도구가, 판단은 사람이

1
근거 없는 추천은 내밀지 않는다 “최적 시간입니다” 대신 “필수 4명 모두 가능 · 준호님은 피하고 싶은 시간”처럼 사람이 읽는 문장으로. 팀 맥락을 아는 건 도구가 아니라 주최자니까.
2
선호는 절대 시간을 막지 않는다 ‘피하고 싶어요’는 색의 진하기와 순서에만 반영돼요. 이게 ‘안 돼요’처럼 작동하면, 사람들은 다시 속마음을 숨기게 되니까요.
3
입력은 ‘보정’만 바쁜 일정은 캘린더가 이미 알아요. 참석자가 할 일은 겹이 모르는 것, ‘마음’을 얹는 것뿐.
04 · 규칙과 제약의 번역

정책·기술 제약을 화면 언어로

일정 도구는 정책(업무시간, 참석 규칙)과 기술 제약(캘린더 권한)이 얽힌 제품이에요. 규칙을 사용자에게 외우게 하지 않고, 화면이 대신 지키게 했어요.

규칙 · 제약화면에서의 번역
업무시간 9–18시, 점심 제외어길 수 있는 옵션이 아니라 후보 자체에서 제외. 만들기 화면에서 미리 고지해 “왜 이 시간이 없지?”를 차단.
필수 참석자 불가 시 확정 불가해당 시간을 빗금 처리하고 “수민님이 안 되는 시간”처럼 누가 막았는지 문장으로. 규칙이 아니라 사정으로 읽히게.
캘린더 권한이 없는 참석자 존재응답 현황에서 ‘캘린더 연동/직접 응답’을 구분 표기. 연동자는 자동 수집, 미연동자에게만 요청 발송.
PC와 모바일의 밀도 차이같은 정보 구조에 컨테이너만 바꿔요. 상세는 PC에선 우측 슬라이드 패널, 모바일에선 바텀시트. 칸의 의미는 ‘그 시각에 시작하는 1시간 회의’로 통일.
확정 후 커뮤니케이션 비용피하고 싶던 시간에 잡힌 동료에겐 양해 메시지, 불참 선택 참석자에겐 회의 노트 공유를 자동 안내.
05 · 검증 계획

출시가 아니라 학습이 끝이다

요청 → 확정 시간 — 기준선 2.3일. H3 검증: 근거 있는 추천 vs 추천만 A/B.
확정 후 재조율률 — 기준선 38%. H1 검증: ‘피하고 싶음’ 사용 팀과 미사용 팀 코호트 비교.
24시간 내 응답률 — H2 검증: 캘린더 프리필 있음/없음 실험.
후보 0건 발생률 — H4 검증: 필수/선택 구분 도입 전후 비교.
숫자가 가설을 기각하면 화면을 되돌릴 수 있도록, 각 가설을 독립된 화면 단위로 설계했어요. 예컨대 H3이 기각되면 추천 카드만 자동 확정형으로 교체하면 돼요.
UI는 토스의 디자인 언어 — 하나의 화면, 하나의 질문 · 큰 타이틀 · 바텀시트/슬라이드 패널 · 단정한 그레이 스케일 — 를 참고해 웹 환경에 맞게 재구성했고, 색·타이포·라운드 토큰은 자체 정의했어요. 프로토타입은 의존성 없는 단일 HTML로, 라이트/다크 테마와 키보드 접근, prefers-reduced-motion을 지원해요. 인용과 수치는 과제용 가상 리서치 설정입니다.
